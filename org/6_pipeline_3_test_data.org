** [Slide 3] Ask: Why set the test set aside before exploring?

- We need to evaluate the model on data it has never seen. Why not look
  at everything first and then split?

** [Slide 4] Answer: biased data means a fake performance measure

#+begin_quote
We need to evaluate the model on data it has never seen to avoid
different forms of *bias*, which would mean that the data set does not
represent the population - and then the performance measure is fake:
the model looks as if it generalizes well but actually it does not.

The test set must be set aside *before* any exploration (*no data
snooping*): looking at the test set biases your intuitions and model
choices.
#+end_quote

** [Slide 7] Answer: two problems with random sampling

Ways to approach this: look at all the operations included in
~train_test_split~:
- randomizing / shuffling
- splitting

#+begin_quote
*Answer 1 - sampling bias*

With a small dataset, random sampling may not represent the full
population - a handful of unlucky rows can skew the test set's income
or location mix. DataCamp's ~train_test_split~ examples avoid this
issue by using clean, balanced datasets; real-world data is rarely
that cooperative. (The fix - stratified sampling - comes in slides
10-14.)

*Answer 2 - the reshuffling trap*

If the script is re-run without a fixed ~random_state~, a different
20% is selected each time. Over multiple runs the model indirectly
sees the *whole dataset* - defeating the purpose of a test set
entirely.

Quick fix: pin ~random_state~ (we use 42 by convention), or save the
test set to disk after the first split and never regenerate it. Its
flaw: if the dataset is refreshed with new instances, the fixed seed
selects a different 20% and the saved test set goes stale.

Robust fix: assign each instance a *hash* of a stable identifier (e.g.
row index or district ID) and always put the same instances in the
test set regardless of dataset order or size - new instances get
assigned by their own hash, old ones stay where they were. The hash
is essentially a *unique key* per row: the same input always produces
the same hash value, so the train/test assignment is deterministic
and stable across dataset updates.
#+end_quote

Fix ~random_state~:

      housing_full, test_size=0.2, random_state=42)

** [Slide 9] Answer: income is correlated with price

#+begin_quote
Both the test and the training data set should be representative of
the full dataset (a sample of the real population of CA districts).

Domain experts say that income is highly correlated with the house
value - if the test set undersamples high or low income districts
randomly, the error estimates will be systematically off.

The problem isn't randomness itself — it's that random doesn't
guarantee balanced, especially for a small or skewed subgroup.

necessarily the mix — and here the mix of incomes is exactly what the
model's accuracy depends on most.

** [Slide 10] → Editor: cut median_income into categories

- Key insight: ~median_income~ is the most important predictor of
  housing price. We must ensure the test set represents its
  distribution faithfully.

  #+begin_src python :results none :exports both :session *Python* :python python3
    import numpy as np

    housing_full["income_cat"] = pd.cut(      # assign to new category column
        housing_full["median_income"],        # pick column
        bins=[0, 1.5, 3.0, 4.5, 6.0, np.inf], # six edges (0,1.5],...(6.0,inf]
        labels=[1, 2, 3, 4, 5])               # name bins 1 through 5
  #+end_src

- Explanation:
  
  #+begin_quote
  ~pd.cut~ turns a continuous numeric column into a categorical one by
  sorting its values into bins:

  - =housing_full["median_income"]= is the column being cut.
  - =bins=[0, 1.5, 3.0, 4.5, 6.0, np.inf]= gives the six edges of five
    bins: (0, 1.5], (1.5, 3.0], (3.0, 4.5], (4.5, 6.0], (6.0, inf]. Each
    bin is a half-open interval - the right edge is included, the left
    edge is not (so 1.5 itself falls into the first bin, not the
    second). =np.inf= as the last edge catches every income above 6, with
    no upper limit.
  - =labels=[1, 2, 3, 4, 5]= names the five bins 1 through 5 instead of
    showing the interval itself (e.g. =(3.0, 4.5]=) - one label per bin,
    in the same order as the edges.
  - The result is assigned to a new column, =housing_full["income_cat"]=
    - a *category* column, not a plain integer column: each value is one
    of the five labels, and the category keeps the bins' order (1 < 2 <
    3 < 4 < 5), which is what lets it be used for stratified sampling.
  #+end_quote

- Answer: because the datasets are different sizes. What stratified
  sampling promises is that *the relative mix of income categories is
  the same in both sets.* If you compare the raw counts, you'd only
  find out that the test set is 20% of the full set (which you already
  knew).

- Mathematically:

  #+begin_quote
  Draw n rows uniformly at random from a population of N, where
  stratum k holds a true share p_k = N_k / N. The count that lands in
  stratum k is random - it follows a *hypergeometric* distribution - and
  its sample proportion X_k / n is unbiased (its average, over many
  random draws, is p_k) but has variance

  Var(X_k / n) = [p_k (1 - p_k) / n] * [(N - n) / (N - 1)]

  For income category 1 (p_k ~ 0.04, N = 20,640, n = 4,128) this gives
  a standard deviation of about 0.0027 - so a single random 20% draw
  typically lands anywhere from about 3.4% to 4.5% for that category,
  a +/-14% swing on the true value. Rare strata are hit hardest,
  because p_k(1-p_k)/n shrinks relative to p_k as p_k grows.

  Stratified sampling with proportional allocation removes this source
  of variance entirely: instead of drawing n rows from the whole
  population, it draws exactly n_k = round(n * p_k) rows from each
  stratum. The test proportion is then

  n_k / n = (n * p_k) / n = p_k

  exactly, up to rounding to a whole row - not a random variable with
  a standard deviation, a fixed number. The only randomness left is
  *which* rows are picked within a stratum, not *how many*.
  #+end_quote
